# STEP 1 — 소형 보안관제 시스템 요구사항

작성 기준: 2026-09-21

## 1. 문서 상태와 기준

- 승인 완료된 [PRD](PRD.md)와 [프로젝트 하네스](project_harness.md)를 요구사항 정리의 기준으로 한다. 행동 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.
- 현재 상태: STEP 1 요구사항 및 사용자 결정 정리 완료, STEP 2 진행 지시 대기. 상세 설계·구현·검증 완료를 의미하지 않는다.
- 아래 기능은 [구현 예정]이다. 완료 조건은 향후 구현 검증 기준이며, 현재 충족했다는 뜻이 아니다.
- 후속 STEP에서 설계할 세부 사항은 임의로 확정하지 않으며, STEP 1의 미결정 사용자 결정과 구분한다. 실제 환경 확인은 [검증 예정]으로 구분한다.
- 사용자 확정 결정은 [결정 기록](00_decisions.md)의 최신 최소 구현안을 따른다. D1~D22의 역할·기술·주요 조건이 지정되었으며 아래에 남긴 세부 사항과 실제 검증은 미완료다. 설계값 지정은 실제 동작 확인을 의미하지 않는다.
- STEP 2는 시작하지 않는다. READY TO CODE 판정과 명시적인 구현 요청 이전에는 개발 작업을 하지 않는다.

## 2. 목적과 확정 범위

보안관제를 공부하는 학생이 실제 공격 이후 로그 수집부터 분석·탐지·대응까지의 연결 과정을 실제 로그와 화면 기록으로 확인하고 설명할 수 있도록 한다.

필수 입력은 Nginx 접속 로그와 Linux SSH 인증 로그 2종이다. 규칙 기반 탐지 3종, 상관분석 최소 1종, 위험도 판단과 보안 사고 구분, SSH 공격자 IP 차단 1종 및 실제 효과 검증을 포함한다. 공격 재현은 통제된 실습·시연 환경 조건이다.

사용자가 제시한 F1~F6 구조를 유지한다. 로그 전달, 이벤트 변환, 탐지, 분석, 대응, 조회의 입력·출력과 완료 조건을 구분하기에 적합하다. 이 구분은 별도 서비스나 배포 단위의 확정이 아니다.

| 그룹 | 기능 | PRD §6 요구사항 번호 |
|---|---|---|
| F1 | 로그 입력·전달·수집 | 1, §7 로그 전달 실패 |
| F2 | 파싱·정규화·보안 이벤트 저장 | 1, 2, 5, §7 정규화 실패 |
| F3 | 탐지·경보 | 3~5 |
| F4 | 상관분석·위험도·보안 사고 | 6, 7 |
| F5 | 자동 대응·효과 확인 | 8~11, 13 |
| F6 | API·대시보드 조회 | 2, 5, 6, 12, §7 대응 실패 확인 |

공통 흐름: 로그 발생 → 로그 전달 → 수집 → 파싱 → 정규화 → 저장 → 탐지 → 경보.

분석 흐름: 경보 → 상관분석 → 위험도 판단 → 기준에 따른 보안 사고 구분.

자동 대응 흐름: 경보 또는 필요한 탐지 결과 → 자동 대응 조건 확인 → 자동 대응 → 결과 기록 → 실제 효과 검증.

자동 대응은 상관분석 또는 보안 사고 생성을 필수 선행 조건으로 하지 않는다. 대시보드는 위 과정의 근거와 결과를 확인하는 화면이다.

## 3. 기능 그룹별 요구사항

### F1. 로그 입력·전달·수집

**목적:** 피해 서버에서 생성된 두 종류의 실제 로그를 관제 서버의 처리 흐름으로 전달한다.

**입력:** 피해 Linux 서버의 Nginx 접속 로그와 Linux SSH 인증 로그. 실제 로그 위치 또는 수집 Source는 피해 서버 환경 확인 후 설계 단계에서 확정한다.

**처리:**

- 피해 서버 rsyslog가 Nginx access.log를 imfile로 읽고 SSH 인증 로그와 함께 TCP 5514로 전달한다. 관제 서버 Python 수집기가 수신한다.
- 관제 서버가 피해 서버의 로컬 로그 파일이나 DB를 직접 공유·마운트해서 읽는 구조를 기본 전제로 삼지 않는다.
- 마지막 로그 수신 시각과 수신 오류를 기록하고 60초 무수신 상태에서 전달 이상을 확인할 수 있게 한다. 60초는 초기 설계값이며 실제 피해 서버 환경 검증 후 필요하면 변경할 수 있다. 무수신만으로 장애 원인을 확정하지 않는다.

**출력:** F2에서 처리할 수집 로그와 로그 전달 실패를 확인할 수 있는 정보. 전달 형식과 상태 표현은 미정이다.

**완료 조건:**

- 피해 서버에서 실제 생성한 두 로그가 관제 서버에 도달하고 F2로 이어지는 것을 확인한다.
- 로그 전달 실패 상황에서 전달되지 않았음을 확인할 수 있다.
- 실제 로그 위치와 전달 경로를 설명할 수 있다.

**후속 설계:** D4의 전달 형식·메시지 경계와 D19의 확인 단위는 STEP 4/5에서 구체화한다. **검증 예정:** 실제 로그 Source(E1), 장비 확보, 학교 LAN·WSL2 연결.

### F2. 파싱·정규화·보안 이벤트 저장

**목적:** 서로 다른 로그 형식을 탐지와 조회가 사용할 공통 보안 이벤트로 변환하고 근거를 보존한다.

**입력:** F1에서 수집한 두 종류의 로그.

**처리:**

- 로그를 파싱하고 공통 보안 이벤트로 정규화해 관제 PostgreSQL에 저장한다.
- 탐지 기능은 원본 로그 형식을 직접 해석하지 않고 정규화된 이벤트를 사용한다.
- 실제 로그에서 얻을 수 있고 탐지·상관분석·조회에 필요한 데이터만 설계한다. 최종 필드와 원본 근거 보관·참조 방식은 STEP 4에서 결정한다.
- 정규화 실패 시 원본 로그와 실패 이유를 별도 실패 기록으로 보존한다. 저장 구조는 후속 설계에서 정한다.

**출력:** 저장된 보안 이벤트, 관련 원본 근거를 확인할 수 있는 정보, 정규화 실패 확인 정보.

**완료 조건:**

- 두 종류의 실제 로그가 공통 이벤트로 저장되고 F3와 F6에서 사용할 수 있다.
- 변환 결과를 실제 로그와 대조하여 필요한 값이 올바르게 반영됐는지 확인한다.
- 탐지 근거가 되는 원본 로그 또는 그 참조를 확인할 수 있다.
- 정규화할 수 없는 입력의 실패 사실을 확인할 수 있다.

**후속 설계:** D5~D8의 URI·시간 처리 세부 기준, D20의 저장 구조, E2·E3·E5. **검증 예정:** 실제 로그 위치·형식(E1).

### F3. 탐지·경보

**목적:** 설명 가능한 규칙 3종으로 의심 행동을 탐지하고 근거가 있는 경보를 만든다.

**입력:** F2의 정규화된 보안 이벤트와 결정된 탐지 규칙·조건.

**처리:**

- SSH 무차별 대입은 동일 출발지 IP에서 60초 안에 인증 실패 5회 이상이면 탐지한다. 사용자 지정 설계값이며 실제 테스트 전이다.
- Nginx 스캔은 동일 IP가 60초 안에 404/403 응답을 발생시키며 서로 다른 URI를 10개 이상 요청하면 탐지한다.
- 세 번째 규칙은 Nginx 의심 경로 접근이다. 초기 목록은 `/.env`, `/wp-admin`, `/wp-login.php`, `/admin`, `/phpmyadmin`, `/.git`, `/config`, `/backup`이다. query string을 제외한 URL path가 해당 경로와 정확히 일치하거나 해당 경로의 하위 경로이면 탐지한다.
- 조건 충족 시 경보를 생성하고 적용 규칙·조건, 출발지 IP, 발생 시간, 관련 로그 근거를 확인할 수 있게 한다.
- 규칙별 입력, 행동 패턴, 묶음 기준, 시간 범위, 횟수 조건, 출력, 중요도, 근거, 오탐 가능성은 STEP 4에서 구체화한다.
- 같은 행동을 탐지와 상관분석에서 중복 계산하지 않도록 역할을 구분한다.

**출력:** 탐지 결과, 조건에 따른 경보, 적용 조건과 실제 로그 근거. F4 및 F5의 입력으로 연결한다.

**완료 조건:**

- 탐지 3종 각각에 대해 실제 로그와 적용 조건을 대조해 경보 발생 이유를 설명한다.
- 조건에 해당하는 입력과 해당하지 않는 정상 입력을 확인하고 오탐 가능성을 기록한다.
- SSH 규칙은 결정된 시간·횟수 기준의 충족 여부와 실제 결과를 대조한다.
- 대표 SSH 시연 성공만으로 Nginx 탐지와 세 번째 규칙의 검증을 대체하지 않는다.

**후속 설계:** URI 정규화 구현 세부, 경보 시간 기준, E2·E5는 STEP 4/5에서 구체화한다. **검증 예정:** 지정 탐지 조건·수치의 실제 검증.

### F4. 상관분석·위험도·보안 사고

**목적:** 관련된 이벤트·경보를 연결하고 설명 가능한 위험도 판단을 통해 보안 사고를 구분한다.

**입력:** F3의 경보와 관련 보안 이벤트, 결정된 상관분석·위험도·보안 사고 기준.

**처리:**

- 동일 출발지 IP의 SSH 무차별 대입 경보와 Nginx 스캔 또는 의심 경로 경보가 10분 이내 함께 발생하면 상관분석이 성립한다.
- 무엇을 어떤 조건으로 연결했는지 근거를 남긴다. 동일 규칙의 반복 횟수 계산만으로 상관분석을 대체하지 않는다.
- 위험도는 0~100 점수와 Low(0~39)/Medium(40~69)/High(70~100)로 표시한다. 현재 판단 대상 안에서 SSH brute force 40, Nginx scan 30, suspicious path 20을 탐지 종류별 1회만 반영하고 지정 상관분석 성립 시 +30을 적용하며 최대 100이다. 동일 종류의 반복 Alert를 발생 횟수만큼 더하지 않는다. 판단 대상 기간과 구현 데이터 구조는 STEP 4에서 정의한다.
- 위험도는 설명 가능한 판단 값이며 침해 확률로 표현하지 않는다.
- 상관분석이 성립하고 위험도가 High(70 이상)이면 Incident를 생성한다. Alert와 Incident는 분리한다.

**출력:** 상관분석 결과와 연관 근거, 위험도 판단 결과와 근거, 기준에 따른 보안 사고 구분 결과.

**완료 조건:**

- 결정된 시나리오로 상관분석 최소 1종의 성립 여부와 연관 이벤트·경보를 확인한다.
- 연관 조건을 충족하지 않는 경우와 구분할 수 있다.
- 위험도 판단과 보안 사고 구분 결과를 결정된 기준으로 설명할 수 있다.
- 대표 SSH 시연에서 상관분석이 반드시 발생한다고 가정하지 않고 별도 검증이 가능하다.

**후속 설계:** 경보 시간 기준, 위험도 판단 대상 기간·데이터 구조, E2·E3·E5 및 별도 상관분석 검증 절차는 후속 STEP에서 구체화한다. STEP 1의 추가 사용자 결정 항목은 없다.

### F5. 자동 대응·효과 확인

**목적:** 조건에 맞는 SSH 공격자 IP를 피해 서버에서 자동 차단하고 실행 결과와 실제 효과를 각각 확인한다.

**입력:** 경보 또는 필요한 탐지 결과, 결정된 자동 대응 조건, 대상 출발지 IP, 허용 목록을 사용하는 경우 해당 목록, 동일 공격자 환경의 SSH 재접속 결과.

**처리:**

- SSH brute force Alert 생성 시 자동 대응 조건이 충족된다. 허용 목록을 확인한 후 관제 서버에서 피해 서버로 SSH 원격 명령을 실행하여 UFW로 공격자 IP의 SSH 접근을 차단한다.
- 상관분석 완료나 보안 사고 생성을 필수 선행 조건으로 두지 않는다.
- 관제 서버 IP와 시스템 관리에 필요한 주소는 자동 차단에서 제외한다. 공격자 Kali IP는 제외하지 않는다. 구체적 IP는 확인 전이다.
- 차단 명령 실행 결과와 실제 효과 검증 결과를 분리 저장한다. UFW에 대상 IP 차단 규칙이 실제 등록되었는지 확인하고 동일 공격자 Kali에서 피해 서버 SSH 재접속을 시도한다. 규칙 존재와 해당 환경의 SSH 접속 실패가 함께 확인되어야 실제 차단 검증 성공으로 기록한다. 단순 접속 실패만으로 성공을 판정하지 않는다.
- 명령 성공만으로 실제 차단 성공을 판정하지 않는다. 검증 실패는 실행 결과와 구분한다.
- 자동 해제 기능은 만들지 않는다. 시연·테스트 종료 후 또는 오탐 시 관리자가 피해 서버에서 수동 해제한다. 별도 승인 화면이나 대응 절차 편집 기능은 추가하지 않는다.
- 대시보드가 꺼졌다는 이유만으로 자동 대응이 멈추는 구조로 설계하지 않는다.

**출력:** 차단 실행 결과, 실제 효과 검증 결과 및 관련 근거. F6에서 조회할 수 있는 기록으로 연결한다.

**완료 조건:**

- 결정된 발동 조건을 충족했을 때 실제 피해 서버에서 대상 IP 차단이 실행된다.
- 발동 조건을 충족하지 않은 경우 자동 차단하지 않으며, 허용 목록을 채택한 경우 제외 동작도 확인한다.
- UFW의 대상 IP 차단 규칙 존재와 동일 Kali 환경의 SSH 재접속 실패를 함께 확인하고 실제 차단 검증 성공을 기록한다.
- 실행 실패와 효과 검증 실패가 구분되어 기록·조회되며, 명령 성공만으로 검증 성공을 표시하지 않는다.
- 관리자가 오탐 차단을 피해 서버에서 수동 해제할 수 있음을 확인한다.
- 상관분석·보안 사고 생성·대시보드 가동을 자동 대응의 필수 선행 조건으로 삼지 않았음을 확인한다.

**후속 설계:** 원격 실행 권한 설계, 대응 결과 저장 구조, E3·E5. **검증 예정:** 실제 SSH 포트·허용 목록 IP·권한 및 차단 동작. STEP 1의 추가 사용자 결정 항목은 없다.

### F6. API·대시보드 조회

**목적:** 학생이 실제 로그부터 분석·대응 결과까지의 근거를 화면으로 확인하고 설명할 수 있게 한다.

**입력:** 저장된 보안 이벤트, 탐지 근거, 경보, 상관분석 결과, 위험도, 보안 사고, 대응 실행·검증 결과.

**처리:**

- Django/DRF API를 통해 React 화면에 필요한 기록을 제공한다. React가 PostgreSQL에 직접 접근하지 않는다.
- 보안 이벤트와 실제 근거, 적용 탐지 조건, 경보와 보안 사고의 구분, 상관분석·위험도 판단, 대응 결과를 확인할 수 있게 한다.
- 대응 실행 결과와 실제 효과 검증 결과를 구분하여 보여준다. 대응 실행 실패도 확인할 수 있어야 한다.
- 화면을 먼저 확정하고 데이터를 억지로 맞추지 않는다. 화면 구성은 STEP 2~3, 데이터·API 명세는 STEP 4에서 구체화한다.

**출력:** 실제 저장 기록을 조회한 API 응답과 관제 화면. 엔드포인트, 필드, 화면 수는 미정이다.

**완료 조건:**

- 두 로그에서 생성된 실제 보안 이벤트가 API를 거쳐 화면에서 확인된다.
- 탐지 조건과 관련 로그, 분석 근거, 경보/보안 사고, 대응 실행·검증 결과를 화면에서 설명할 수 있다.
- 화면의 결과가 저장된 실제 기록과 일치한다. Mock Data 화면만으로 완료로 판단하지 않는다.
- 최종 시연에서 대표 공격 1회 이상을 실제 로그와 화면 기록으로 순서대로 설명할 수 있다.

**후속 설계:** 판단 대상 기간·데이터 구조, D18의 저장 구조, E2~E4와 실패 상태 표현을 후속 STEP에서 구체화한다. STEP 1의 추가 사용자 결정 항목은 없다.

## 4. 공통 완료 기준과 제약

- 대표 시연은 통제된 환경의 SSH 인증 실패 반복 → 실제 로그 → 정규화된 이벤트 → 탐지 근거 → 경보 → 분석 결과 확인 → 자동 대응 → 동일 환경 재접속을 통한 실제 차단 확인이다. 이는 기록 설명 순서이며 분석 완료를 자동 대응의 필수 조건으로 만드는 실행 순서가 아니다.
- 탐지 3종과 상관분석 최소 1종을 각각 검증한다. 학생의 설명 가능성은 실제 로그와 화면 기록으로 확인하며 별도의 사용자 설문·평가를 추가하지 않는다.
- 로그 전달 실패, 정규화 실패, 자동 대응 실패, 실제 차단 검증 실패를 확인할 수 있어야 한다. 세부 처리 정책은 미정으로 남긴다.
- 정상 입력·잘못된 입력, 결과, 연결 기능 영향을 확인한다. 탐지 근거·오탐 가능성·탐지 지연 등 검증 결과를 남기되 임의의 성능 목표 수치는 정하지 않는다.
- 공격자·피해 서버·관제 서버는 서로 다른 장비에 배치하며 같은 학교 LAN을 사용할 수 있다. VLAN·별도 서브넷은 만들지 않는다. 피해 시스템 데이터와 관제 데이터는 논리적으로 분리한다. 관제 서버 자체 PostgreSQL에 보안 이벤트와 탐지·분석·대응 결과를 저장한다. 피해 서버에는 로그인·DB를 만들지 않고 Nginx 로그 생성용 최소 웹 서비스만 둔다.
- 기술 스택: Python, Django 5.2 계열, DRF, React, Vite, PostgreSQL 16 계열, Docker, Docker Compose, WSL2 Ubuntu, Linux. 형상 관리는 Git/GitHub이나 현재 단계에서는 Git 작업을 하지 않는다.
- 인원 3명, 핵심 기능 완성 목표 2026-10-05 전후, 최종 완성 목표 2026-10-15를 유지한다.
- 상용 SIEM/SOAR 전체 기능, 복잡한 승인·대응 편집 화면, 통제되지 않은 외부 환경 공격은 범위 밖이다. 추가 로그 Source나 큰 추가 기술을 도입하지 않는다.
- 비밀번호·토큰 등 비밀정보를 문서나 코드에 직접 저장하지 않는다.
- 기존 기반 환경과 Mock UI의 과거 확인 기록은 하네스의 설명이다. 이번 문서 작업에서 실제 구현 상태를 새로 검증하지 않았으며, 기존 UI를 실제 데이터 대시보드 완료로 취급하지 않는다.

## 6. STEP 1 재검토 결과

최소 구현안은 사용자 설계 결정으로 반영했다. PRD에서 테스트 후 결정하도록 남겼던 SSH 수치와 자동 해제 정책도 이번 사용자 결정으로 지정했으며 실제 검증은 아직 수행하지 않았다. 변경이 필요하면 사용자에게 보고한다.

**STEP 1 추가 사용자 결정:** 없음. F1~F6에 목적·입력·처리·출력·완료 조건을 정리했고, D1~D22의 STEP 1 수준 사용자 결정을 반영했다. 요구사항 정리와 사용자 결정 단계로서 STEP 1을 완료했다.

**후속 STEP 설계:** STEP 2~3의 흐름·화면 구조, STEP 4의 위험도 판단 대상 기간·데이터 스키마·API·시간 및 URI 처리 세부, STEP 4/5의 전달 형식·TCP 메시지 경계·무수신 확인 단위·권한·예외 정책·검증 절차. 이 항목들은 STEP 1의 미결정 사용자 결정이 아니다.

**검증 예정:** 피해 장비 대여·확보, 실제 학교 LAN·WSL2 연결, 로그 위치·형식, 포트·허용 목록 IP·권한과 실제 탐지·상관분석·대응 동작. 실제 환경 검증 전이라는 사실을 설계 결정 미완료로 취급하지 않는다.

**진행 상태:** STEP 2 진행 가능. 사용자의 진행 지시를 기다리며 아직 시작하지 않는다. STEP 1 완료는 READY TO CODE 또는 구현·통합 검증 완료를 의미하지 않는다.
