# STEP 5 — 기술·보안 설계

작성 기준: 2026-09-21

## 1. 설계 상태와 시스템 경계

이 문서는 확정된 기능을 실제 환경에 연결하기 위한 기술·보안 기준이다. 실제 장비 확보, 네트워크 연결, 로그 위치·형식, IP, SSH 포트, 권한과 동작은 아직 확인하지 않았으며 `[검증 예정]`으로 표시한다. 임의의 실제 값을 문서에 넣지 않는다.

```text
[학교 PC WSL Kali 공격자]
          │ 통제된 SSH 실습
          ▼
[학교 Ubuntu 미니 PC 피해 서버]
  Nginx / sshd / rsyslog / UFW
          │ 네트워크 로그 전달(TCP 5514)
          ▼
[개인 노트북 WSL2 Ubuntu 관제 서버]
  Python 수집기 → Django/DRF → PostgreSQL
                         │
                         ▼
                    React + Vite
```

- 공격자·피해 서버·관제 서버는 서로 다른 장비에 배치하고 같은 학교 LAN을 사용할 수 있다. VLAN이나 별도 서브넷은 추가하지 않는다.
- 피해 서버와 관제 서버는 PostgreSQL을 공유하지 않는다. 관제 서버 자체 PostgreSQL에 정규화된 보안 이벤트와 탐지·분석·대응 결과를 저장한다.
- 피해 웹서비스용 로그인·DB는 만들지 않으며 Nginx 로그 생성용 최소 웹서비스만 사용한다.
- 관제 서버가 피해 서버의 로컬 로그 파일이나 DB를 공유·마운트해 읽는 구조를 사용하지 않는다. 로그는 네트워크로 전달한다.

## 2. 로그 수집과 전달

- 피해 서버의 `rsyslog`가 Nginx `access.log`를 `imfile`로 읽고 Linux SSH 인증 로그도 전달한다.
- 전달 대상은 TCP 5514이며 관제 서버의 Python 수집기가 수신한다.
- 실제 SSH 인증 로그 위치, Nginx 로그 형식, rsyslog 입력 설정, 학교 LAN에서 WSL2 수집기까지의 연결은 `[검증 예정]`이다.
- 관제 서버는 source_type별 마지막 수신 시각과 수신 오류를 기록한다. 60초 무수신은 전달 이상 표시 기준이며 원인 확정값이 아니다.
- 로그 문자열은 수집·정규화 전에 원본 근거로 보존할 수 있어야 한다. 원본 로그를 shell 명령이나 SQL 문자열로 직접 조합하지 않는다.

## 3. 애플리케이션과 데이터 경로

| 계층 | 기술·역할 |
|---|---|
| Backend | Python, Django 5.2 계열, Django REST Framework |
| Frontend | React, Vite |
| Database | PostgreSQL 16 계열, 관제 서버 전용 |
| 실행 | Docker, Docker Compose, WSL2 Ubuntu, Linux |
| 데이터 경로 | React → Django/DRF → PostgreSQL |

React는 PostgreSQL에 직접 접근하지 않는다. API는 A~D 화면의 최소 조회만 제공하고 자동 대응 실행, 공격 실행, 규칙 편집, Playbook, 승인 API를 만들지 않는다. 화면 조회 장애가 자동 대응 백엔드의 실행 조건이 되어서는 안 된다.

## 4. 자동 대응 보안 설계

1. SSH brute force Alert가 생성되면 백엔드가 자동 대응 조건을 확인한다. 상관분석이나 Incident 생성을 기다리지 않는다.
2. 관제 서버가 허용 목록을 먼저 검사한다. 관제 서버 IP와 시스템 관리에 필요한 주소는 제외하고, 공격자 Kali IP는 제외하지 않는다. 실제 IP 목록은 `[검증 예정]`이다.
3. 조건을 충족한 경우 관제 서버에서 피해 서버로 SSH 원격 명령을 실행해 UFW로 공격자 IP의 SSH 접근을 차단한다.
4. 실행 상태·출력·오류를 ResponseRecord에 저장하고, UFW 규칙 확인과 동일 Kali SSH 재접속은 ResponseVerification에 별도 저장한다.
5. UFW 규칙 존재와 동일 Kali의 SSH 접속 실패가 함께 확인될 때만 실제 차단 검증 성공으로 기록한다. 명령 성공이나 단순 접속 실패만으로 성공 판정하지 않는다.
6. 자동 해제는 만들지 않는다. 시연·테스트 종료 또는 오탐 시 관리자가 피해 서버에서 수동 해제한다.

실제 SSH 계정·키·포트·권한은 `[검증 예정]`이며, 대응 계정은 필요한 최소 권한만 부여한다. 비밀번호, 토큰, SSH private key를 코드·문서·Git에 저장하지 않고 환경변수나 안전한 로컬 설정을 사용한다.

## 5. 입력 검증과 최소 권한

- 차단 대상 IP는 IP 형식 검증을 통과한 값만 사용한다.
- 허용 목록을 차단 명령보다 먼저 검사한다.
- 사용자 입력이나 로그 문자열을 shell command에 직접 이어붙이지 않는다. 명령 인자와 실행 경로를 고정된 방식으로 구성하고 오류를 기록한다.
- SSH 원격 대응 계정에는 필요한 원격 명령과 UFW 조작에 필요한 최소 권한만 부여한다. 권한 부여 방식은 `[검증 예정]`이다.
- API는 저장된 기록만 반환하고 원본 로그에 포함된 비밀정보가 화면·오류 응답에 불필요하게 노출되지 않도록 마스킹 범위를 검토한다.
- 실제 공격은 학교 소유의 통제된 실습·시연 환경에서만 수행한다. 외부 임의 IP를 대상으로 하지 않는다.

## 6. 실패·예외 처리 기준

| 상황 | 최소 처리 기준 |
|---|---|
| 로그 수신 오류 | 수신 오류와 마지막 수신 시각 기록 |
| 60초 무수신 | 전달 이상 표시만 함. 장애 원인을 확정하지 않음 |
| 정규화 실패 | 원본 로그와 실패 이유를 NormalizationFailure로 보존 |
| DB 저장 실패 | 저장 실패 사실과 관련 오류를 기록하고 성공 저장으로 표시하지 않음 |
| 중복 로그 | 동일 이벤트가 무한히 중복 생성되지 않도록 최소 중복 방지를 구현 단계에서 확인 |
| 순서 역전·지연 | 수신 시각과 원본 event_time을 구분해 기록·표시 |
| SSH/UFW 명령 실패 | 실행 상태와 오류를 ResponseRecord에 기록 |
| 효과 검증 미수행·실패 | `unverified`·`failed`·`success`를 구분하고 실행 성공과 합치지 않음 |
| API 조회 실패 | 빈 데이터나 분석·대응 실패와 구분한 조회 오류로 표시 |

중복 판정 키, 재처리 정책, 저장 실패 재시도, 순서 역전의 세부 기준은 실제 로그와 구현을 확인하는 단계에서 정한다. 새로운 기능을 추가하지 않는다.

## 7. `[검증 예정]` 환경 항목

- 교수님 대여 예정인 Ubuntu 미니 PC의 실제 확보·접속·배포판·로그 경로.
- 학교 LAN에서 피해 서버와 개인 노트북 WSL2 간 TCP 5514 연결.
- 실제 Nginx access.log와 SSH 인증 로그 형식.
- 피해 서버·관제 서버·공격자 IP, 실제 SSH 포트, UFW 상태.
- 원격 SSH 대응 계정·키·최소 권한과 명령 실행 결과.
- 두 로그의 실제 수집부터 탐지·대응·효과 검증까지의 동작.

이 항목들은 설계 결정 누락이 아니라 Phase 1~5에서 환경을 확인하기 위한 검증 작업이다.
