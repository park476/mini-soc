======================================================================
0. 이 문서를 읽는 GPT에게
======================================================================

이 문서는 이전 대화 전체를 다음 프로젝트 진행 세션으로 넘기기 위한 요약이다.

새 GPT는 아래 내용을 이미 사용자와 합의된 프로젝트 맥락으로 취급하되,
실제 코드, 실제 서버 환경, 실제 버전, 실제 오류 메시지 등은 이후 사용자가 제공하는 최신 정보를 최우선으로 한다.

중요:
- 사용자의 실력을 실제보다 높게 가정하지 않는다.
- 사용자는 과거 공부 내용을 상당히 잊었을 수 있다.
- 프로젝트는 명목상 3인이지만 사실상 1인 개발을 기준으로 설계한다.
- Frontend도 최종적으로 사용자가 직접 맡을 가능성을 항상 고려한다.
- 마감일과 완성이 최우선이다.
- 복잡한 기술 추가보다 End-to-End 동작을 우선한다.
- 실제 Credential, 초기 비밀번호, SSH 비밀번호, Secret은 이 문서에 저장하지 않는다.
- 학교 서버 접속정보가 필요하면 사용자가 별도로 안전하게 제공하거나 로컬 설정에서 사용하도록 한다.

1. 사용자 상황
======================================================================

전공:
- 정보보안학과
- 전문대 2학년 졸업 프로젝트

학습/실력 상태:
- 사용자는 2024년 상반기까지 공부하다가 군 복무 후 복학했다.
- 장기간 공백으로 Python, 웹, 네트워크, DB, Linux, Git, Django, React, 보안 개념 등을 많이 잊었을 가능성이 있다.
- 사용자의 실력을 "전문대 2학년이면 이 정도는 당연히 알 것"이라고 가정하지 않는다.
- 이미 알 법한 내용도 프로젝트 구현에 중요하면 짧게 복습한 뒤 구현으로 연결한다.
- 단, 매번 기초부터 장황하게 반복하지 않는다.
- 가장 좋은 학습 방식은 "현재 구현에 필요한 만큼 복습 → 구현 → 실행 → 오류 수정 → 다시 이해 → 다음 기능"이다.

사용자의 최우선 목표:
1. 졸업 프로젝트를 제때 완성
2. 취업에 도움이 되는 포트폴리오 확보
3. 단순 도구 연결이나 껍데기 프로젝트가 아니라 실제 내부 로직이 탄탄한 프로젝트
4. 사용자가 면접/발표에서 직접 원리를 설명할 수 있는 프로젝트

사용자 선호:
- 전문가 연구 수준의 난이도는 피하고 싶음.
- 너무 쉬운 CRUD/툴 래핑/깡통형 프로젝트도 피하고 싶음.
- 취업 실무와 연결되는 기술을 프로젝트에서 증명하고 싶음.
- 필요하면 AI Coding Tool을 적극 활용할 생각임.

2. 팀 상황
======================================================================

명목상:
- 3인 1조

실질 상황:
- 사용자 본인이 핵심 개발을 사실상 책임질 가능성이 매우 높음.
- 팀원 1명은 취업으로 학교에 거의 나오지 않는 상태라 핵심 개발 전력으로 계산하지 않음.
- 다른 팀원 1명은 편입 준비 중이고 프로젝트 개발 지식이 많지 않아 보임.
- 해당 팀원에게 Frontend를 맡길 가능성은 있으나, 실제로 잘 수행할 수 있을지는 불확실함.
- 따라서 Frontend까지 사용자 본인이 인수할 가능성을 항상 고려해야 함.

설계 원칙:
- 다른 팀원의 작업을 Critical Path에 배치하지 않는다.
- 다른 팀원이 아무것도 하지 못해도 핵심 Demo가 완성되어야 한다.
- 다른 팀원이 기여하면 일정 단축 또는 완성도 향상으로 취급한다.
- 팀원에게 맡길 경우 독립적인 UI 단위, 테스트, 문서, 데이터 정리 등으로 작업을 잘게 자른다.

7. Django를 선택한 이유

현재 프로젝트에서는 Django + DRF가 FastAPI보다 현실적인 기본 선택으로 판단됨.

- Migration
- Authentication
- Admin

- 빠른 CRUD 개발

- Django는 중앙 Backend Platform 역할.
- 핵심 Security Logic은 독립 Module로 유지.

Frontend는 PostgreSQL에 직접 접근하지 않는다.
Frontend는 /api/* 만 사용한다.

초기 API 후보:
- GET /api/dashboard/summary
- GET /api/events
- GET /api/events/{id}
- GET /api/alerts
- GET /api/alerts/{id}
- GET /api/incidents
- GET /api/incidents/{id}
- GET /api/detection-rules

후반 필요 시:
- POST /api/incidents/{id}/close
- POST /api/playbooks/{id}/execute

팀원이 Backend를 기다리지 않고 개발하도록:
- API Response Schema 먼저 정의
- Mock Data 제공
- Frontend는 Mock으로 개발
- 실제 Backend 완성 후 API Client만 교체

팀원에게 맡기기 좋은 범위:
- Layout
- Dashboard
- Table

- Search

팀원에게 처음부터 맡기기 위험한 범위:

15. 추천 탐지 Rule
======================================================================

우선 3개:

1. SSH Brute Force
- 일정 시간 내 동일 Source IP에서 다수 LOGIN_FAILURE

2. Web Path / Directory Scanning
- 짧은 시간 동안 다수의 서로 다른 Path 요청
- 404 다량 발생 등의 패턴 활용 가능

3. Suspicious Login / Account Compromise
- 반복 실패 이후 성공
- Correlation 시나리오와 연결 가능

Rule마다 반드시 설명:
- Input Event
- Pattern
- Time Window
- Grouping Key
- Threshold
- Output Alert
- Severity
- False Positive 가능성

16. Correlation
======================================================================

Mini SOC의 핵심 차별 요소 중 하나.

Detection:
- 단일 Event 또는 동일 Event 반복을 판단

Correlation:
- 종류가 다른 Event를 시간, IP, Username 등의 관계로 연결

추천 시나리오:

동일 Source IP
→ 일정 시간 내 LOGIN_FAILURE 반복
→ LOGIN_SUCCESS
→ 중요 Endpoint/관리자 Resource 접근
→ Risk 상승
→ Incident 생성

최소 1개를 제대로 구현하는 것이 탐지 Rule을 20개 만드는 것보다 낫다.

======================================================================
17. Risk Score
======================================================================

0~100 또는 LOW/MEDIUM/HIGH/CRITICAL.

임의 숫자가 아니라 설명 가능한 기준 필요.

사용 가능 요소:
- Rule Severity
- 반복 횟수
- 시간 Window
- 관련 Alert 수
- 공격 성공 여부
- 민감 Resource 접근
- Correlation 성립 여부

예시:
Brute Force +20
Success after Brute Force +30
Admin Access +40
= 90 / CRITICAL

실제 공식은 테스트를 보며 확정.

======================================================================
18. Alert와 Incident
======================================================================

Alert:
- 특정 Detection Rule에 의해 생성되는 경고

Incident:
- 관련 Event/Alert 여러 개를 하나의 보안 사건으로 묶음

예:
SSH_BRUTE_FORCE → Alert A
SUSPICIOUS_LOGIN → Alert B
동일 IP/User/시간 흐름 → Account Compromise Incident

======================================================================
19. Response Playbook
======================================================================

초기에는 1개만 제대로.

후보:
- 테스트 환경 공격 Source IP 차단

흐름:
Detection
→ Alert/Incident
→ Response Condition
→ Playbook
→ Block IP
→ Result 저장
→ 동일 공격 재시도
→ 차단 검증

주의:
- False Positive 위험 있음.
- 자동 차단이 실제 운영에서 항상 정답이라고 주장하지 않음.
- 테스트 환경에서 수행.
- 실행 이력/Audit Log 남기면 좋음.

46. 새 GPT가 반드시 유지해야 할 행동 원칙
======================================================================

1. 사용자의 실력을 실제보다 높게 가정하지 않는다.
2. 사용자는 개발/보안 내용을 많이 잊었을 수 있다.
3. 필요한 개념은 구현과 연결해서 다시 설명한다.
4. 한 번에 너무 많은 작업을 던지지 않는다.
5. 1단계 성공 후 다음 단계로 간다.
6. 프로젝트는 사실상 1인 개발 기준.
7. Frontend까지 사용자가 직접 맡을 수 있음.
8. 팀원 완료를 Critical Path로 잡지 않는다.
9. 여러 Windows PC와 Linux 서버를 오갈 수 있어야 한다.
10. 학교 서버는 학교 내에서만 SSH 가능하므로 서버 종속 금지.
11. 서버 OS는 실제 확인 전 추측 금지.
12. 실제 Credential/Secret을 문서나 코드에 넣지 않는다.
13. AI Coding Tool은 적극 활용 가능.
14. 하지만 AI가 Architecture를 멋대로 바꾸게 하지 않는다.
15. 새로운 기술 추가보다 End-to-End 완성을 우선한다.
16. 매주 발표 가능한 실행 결과를 남긴다.
17. 10월 5일 전후 핵심 Feature Freeze 지향.
18. 10월 15일 완성 최우선.
19. 기능 수보다 수집→탐지→대응→검증 흐름을 우선한다.

47. 다음 세션에서 가장 먼저 해야 할 일
======================================================================

아직 실제 개발 시작 전이라면 다음 순서를 권장:

1. Mini SOC v1.0 범위를 최종 동결
2. Repository 생성
3. 개발 환경 결정
   - 메인 Windows + WSL2 권장
4. Django + React + PostgreSQL 기본 골격
5. docker-compose 최소 구성
6. SecurityEvent Schema 1차 확정
7. API Contract 1차 확정
8. Nginx → Collector → Normalizer → DB → API → React Table 최초 Vertical Slice 완성

이 최초 Slice가 성공하기 전에는:
- AI 기능
- ML
- Elasticsearch
- 많은 탐지 규칙
- 예쁜 Dashboard
를 우선하지 않는다.

48. 핵심 한 문장
======================================================================

기능을 많이 붙이는 것보다,

"실제 로그가 수집되고, 서로 다른 형식의 로그가 공통 이벤트로 정규화되고, 설명 가능한 규칙으로 공격이 탐지되며, 관련 이벤트가 상관분석되고, 위험도가 계산되고, Incident와 대응으로 이어지고, 그 결과를 직접 시연하고 측정할 수 있는 하나의 완성된 보안 흐름"

을 만드는 것을 항상 우선한다.
