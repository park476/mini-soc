### 1. 개요

보안관제를 공부하는 학생이 실제 공격 이후 로그 수집부터 분석·탐지·대응까지의 연결 과정을 직접 확인하고 설명할 수 있도록 소형 보안관제 시스템을 구현한다.

필수 입력은 **Nginx 접속 로그와 Linux SSH 인증 로그 2종**이다. 설명 가능한 규칙 기반 탐지 **3종**, 상관분석 최소 1종, 위험도 판단과 보안 사고 구분, 제한적인 자동 대응 1종 및 실제 효과 검증을 포함한다.

전체 분석의 기본 흐름은 다음과 같다.

**로그 수집·전달 → 정규화된 보안 이벤트 → 규칙 기반 탐지 → 경보 → 상관분석 → 위험도 판단 → 보안 사고**

자동 대응은 다음의 별도 흐름으로 수행할 수 있다.

**경보 또는 필요한 탐지 결과 → 자동 대응 조건 확인 → 자동 대응 → 실제 효과 검증**

자동 대응을 반드시 상관분석과 보안 사고 생성 이후에만 수행하도록 제한하지 않는다.

SSH 무차별 대입 공격은 대표 시연 시나리오이며 전체 프로젝트 범위를 SSH로 한정하지 않는다. 공격 재현은 제품 기능이 아닌 통제된 실습·시연 환경 조건이다.

### 2. 목표와 성공 기준

**목표**

보안관제를 공부하는 학생이 실제 로그와 시스템 화면의 기록을 이용해 공격부터 분석·대응 결과까지의 연결 과정을 확인하고 설명할 수 있게 한다.

**성공 기준**

1. Nginx 접속 로그와 Linux SSH 인증 로그 2종이 관제 서버로 수집·전달되고, 정규화된 보안 이벤트로 확인된다.
2. 설명 가능한 규칙 기반 탐지 **3종을 구현·검증**하고, 각 규칙의 탐지 조건과 실제 로그 근거를 확인할 수 있다.
   - SSH 무차별 대입 탐지
   - Nginx 로그 기반 탐지
   - 설계 단계에서 종류를 결정할 나머지 탐지 1종
3. 상관분석 최소 1종이 동작하며, 어떤 이벤트·경보를 어떤 조건으로 연관 지었는지 확인할 수 있다. 대표 SSH 시연과 별도의 검증 시나리오로 확인할 수 있다.
4. 위험도 판단 결과와 경보/보안 사고의 구분을 확인할 수 있다. 판단 기준과 계산식은 설계 중 결정한다.
5. 제한적인 자동 대응 1종이 조건 충족 시 실행되고, 실행 결과와 실제 효과 검증 결과를 각각 확인할 수 있다.
6. 대시보드에서 보안 이벤트, 탐지 근거, 경보/보안 사고, 대응 결과를 확인할 수 있다.
7. 최종 시연에서 대표 공격 **1회 이상**에 대해 다음 과정을 실제 로그와 시스템 화면의 기록으로 순서대로 확인할 수 있다.

   **공격 발생 → 실제 로그 → 정규화된 보안 이벤트 → 탐지 근거 → 경보 → 분석 결과 → 자동 대응 → 실제 차단 확인**

   이 확인 순서는 시연에서 기록을 설명하는 순서이며, 자동 대응이 반드시 상관분석이나 보안 사고 생성을 기다린다는 뜻은 아니다. 대표 시연에서 상관분석이 반드시 발생한다고 가정하지 않는다.

학생의 설명 가능성은 위 시연 기록으로 확인하며, 주관적 설문이나 별도의 사용자 평가는 추가하지 않는다. 대표 SSH 시연의 성공만으로 전체 탐지와 상관분석의 검증을 대체하지 않는다.

### 3. 대상 사용자

보안관제를 공부하며 실제 공격 이후 로그 분석부터 탐지와 대응까지의 전체 과정을 실습하고 이해하려는 학생.

### 4. 문제 정의

보안관제를 공부하는 학생은 실제 공격이 발생한 뒤 로그가 수집·분석되고 탐지와 대응으로 이어지는 전체 과정을 직접 확인하고 설명하기 어렵다.

### 5. 범위

**In Scope**

- Nginx 접속 로그와 Linux SSH 인증 로그의 수집·전달 및 정규화
- 설명 가능한 규칙 기반 탐지 3종: SSH 무차별 대입, Nginx 로그 기반 탐지, 설계 중 결정할 나머지 1종
- 경보 생성과 상관분석 최소 1종
- 위험도 판단 및 경보/보안 사고 구분
- 경보 또는 필요한 탐지 결과를 바탕으로 한 자동 대응 조건 확인
- 제한적인 자동 대응 1종인 피해 서버의 SSH 공격자 IP 차단
- 대응 실행 결과와 실제 차단 효과의 검증·기록
- 대시보드에서 보안 이벤트, 탐지 근거, 경보/보안 사고, 대응 결과 확인
- 오탐 시 관리자가 피해 서버의 차단 기능에서 IP를 수동 해제하는 운영 방식
- 필요 시 자동 차단 제외 대상인 허용 목록 지원

**실습·시연 환경 조건**

통제된 공격자 환경에서 피해 Linux 서버에 SSH 인증 실패를 반복 발생시키고, 차단 이후 같은 환경에서 SSH 접속을 재시도한다.

대표 SSH 시연은 자동 대응 흐름 검증에 사용한다. Nginx 로그 기반 탐지, 세 번째 탐지 규칙 및 상관분석의 구체적인 검증 시나리오는 설계 중 결정한다. 상관분석은 대표 SSH 시연과 별도로 검증할 수 있다.

**Out of Scope**

| 제외 항목 | 이유 |
|---|---|
| 상용 SIEM/SOAR 전체 기능 구현 | 3명이 일정 안에서 구현·시연할 수 있는 규모를 유지하기 위함 |
| 복잡한 승인 화면과 별도 대응 절차 편집 기능 | 제한적인 자동 대응 1종의 구현과 검증에 집중하기 위함 |
| 통제되지 않은 외부 환경에 대한 공격 | 실습·시연을 학교 또는 개인 소유의 통제된 환경으로 한정하기 위함 |

상용 제품 전체 기능 제외는 위에 명시한 탐지·상관분석·위험도 판단·보안 사고 구분을 제외한다는 의미가 아니다.

### 6. 요구사항

1. 시스템은 Nginx 접속 로그와 Linux SSH 인증 로그를 관제 서버로 수집·전달하고 정규화해야 한다.
2. 사용자는 정규화된 보안 이벤트를 대시보드에서 확인할 수 있어야 한다.
3. 시스템은 설명 가능한 규칙 기반 탐지 3종을 제공해야 한다. SSH 무차별 대입 탐지와 Nginx 로그 기반 탐지를 포함하며, 나머지 1종은 설계 중 결정한다.
4. SSH 탐지는 동일 출발지 IP에서 설정된 시간 범위 안에 설정된 횟수 이상의 인증 실패가 발생했는지 판단해야 한다. 시간과 횟수는 실제 테스트 후 확정한다.
5. 시스템은 규칙 기반 탐지 결과에 따라 경보를 생성해야 한다. 사용자는 적용된 탐지 조건과 출발지 IP, 발생 시간, 관련 로그 등 근거를 확인할 수 있어야 한다.
6. 시스템은 경보 이후 상관분석 최소 1종을 제공하고, 연관된 이벤트·경보와 판단 근거를 확인할 수 있게 해야 한다.
7. 시스템은 상관분석 이후 위험도를 판단하고 보안 사고로 구분할 수 있어야 한다. 구체적인 상관분석 조건, 위험도 계산 기준과 보안 사고 구분 기준은 설계 중 결정한다.
8. 시스템은 경보 또는 필요한 탐지 결과를 바탕으로 자동 대응 조건을 확인할 수 있어야 한다. 상관분석 완료나 보안 사고 생성을 자동 대응의 필수 선행 조건으로 제한하지 않아야 한다.
9. SSH 공격자 IP 차단 조건이 충족되면 별도 사람 승인 없이 피해 서버에서 해당 출발지 IP를 차단해야 한다.
10. 허용 목록을 사용하는 경우 해당 IP는 자동 차단에서 제외해야 한다. 적용 여부와 구체적인 범위는 추후 결정한다.
11. 차단 실행 성공·실패와 동일 공격자 환경의 재접속을 통한 실제 차단 검증 결과를 구분해 기록해야 한다. 차단 명령 성공만으로 실제 차단 성공을 판정하지 않아야 한다.
12. 사용자는 대시보드에서 보안 이벤트, 탐지 근거, 상관분석 결과, 위험도, 경보/보안 사고, 대응 결과를 확인할 수 있어야 한다.
13. 오탐으로 판단된 IP는 관리자가 피해 서버의 차단 기능에서 수동 해제할 수 있어야 한다. 별도의 승인 화면이나 대응 절차 편집 기능은 요구하지 않는다.

### 7. 사용자 시나리오

**기본 분석 흐름**

1. 실습 환경에서 Nginx 접속 로그와 Linux SSH 인증 로그가 생성된다.
2. 시스템이 두 로그를 관제 서버로 수집·전달하고 정규화된 보안 이벤트로 만든다.
3. 시스템이 규칙 기반 탐지를 수행하고 조건에 해당하면 경보를 생성한다.
4. 시스템이 경보 이후 상관분석을 수행한다.
5. 위험도를 판단하고 기준에 따라 보안 사고로 구분한다.
6. 사용자는 대시보드에서 보안 이벤트, 탐지 근거, 경보, 상관분석 결과, 위험도 및 보안 사고를 확인한다.

**자동 대응 흐름**

1. 경보 또는 필요한 탐지 결과를 바탕으로 자동 대응 조건을 확인한다.
2. 조건이 충족되면 제한적인 자동 대응을 실행한다.
3. 대응의 실제 효과를 검증한다.
4. 사용자는 대시보드에서 대응 실행 결과와 검증 결과를 각각 확인한다.

자동 대응 흐름은 상관분석과 보안 사고 생성이 완료된 경우에만 시작하도록 제한하지 않는다.

**대표 SSH 시연**

1. 통제된 공격자 환경에서 피해 서버의 SSH 로그인을 반복 실패시킨다.
2. 피해 서버의 Linux SSH 인증 로그에 인증 실패 기록이 남고 관제 서버로 전달·정규화된다. 실제 로그 위치 또는 수집 Source는 피해 서버 환경 확인 후 설계 단계에서 확정한다.
3. 동일 출발지 IP의 인증 실패가 설정 기준에 도달하면 경보가 생성된다.
4. 시스템이 자동 대응 조건과 적용된 차단 제외 대상을 확인한다.
5. 조건을 충족하면 사용자 승인 없이 피해 서버에서 공격자 IP를 차단한다.
6. 동일 공격자 환경에서 SSH 접속을 재시도해 실제 차단 여부를 검증한다.
7. 실제 로그와 시스템 화면의 기록을 이용해 공격, 보안 이벤트, 탐지 근거, 경보, 분석 결과, 자동 대응 및 실제 차단 확인 과정을 순서대로 설명한다.

대표 SSH 시연에서 상관분석이 반드시 발생한다고 가정하지 않는다. 상관분석 최소 1종은 별도의 검증 시나리오로 확인할 수 있다.

**잘못될 수 있는 것**

| 실패 상황 | 시스템 반응 또는 확인 방식 |
|---|---|
| 로그 전달 실패 | 전달되지 않은 상태를 확인할 수 있어야 한다. 구체적인 처리 방식은 설계 중 결정한다. |
| 정규화 실패 | 정규화 실패 사실을 확인할 수 있어야 한다. 해당 로그의 처리 방식은 설계 중 결정한다. |
| 자동 대응 실패 | 대응 실행 실패를 기록하고 대시보드에서 확인할 수 있어야 한다. |
| 실제 차단 검증 실패 | 차단 실행 결과와 구분해 검증 결과를 기록하며, 실제 차단 성공으로 판정하지 않는다. |

로그 지연, 순서 뒤바뀜, 중복 경보, 결과 저장 실패 등의 세부 예외 처리 정책은 이후 설계 단계에서 다룬다.

**지금 결정할 것 — PRD 합의 단계**

이번 결정으로 탐지의 최종 구현·검증 목표는 3종으로 확정했다. 학생의 설명 가능성 확인 방법도 대표 공격 1회의 실제 로그와 시스템 화면 기록을 통한 순차 확인으로 확정했다.

이 PRD는 사용자 승인 완료 상태다.

**설계 중 결정할 것**

- Nginx 로그 기반 탐지 규칙의 구체적인 조건과 근거
- 세 번째 탐지 규칙의 구체적인 종류
- 상관분석 대상·조건과 별도 검증 시나리오
- 위험도 계산 기준과 보안 사고 구분 기준
- 자동 대응 조건과 그 판단에 사용할 경보 또는 탐지 결과
- 장비별 역할과 로그 수집·전달 기술
- 실제 IP 차단 기술과 허용 목록 적용 방식
- 실제 차단 검증 절차와 결과 기록 방식
- 로그 전달 실패·정규화 실패 등의 처리 방식과 세부 예외 정책

→ 피해 서버 환경과 실제 로그를 확인하고, 관련 구현에 들어가기 전에 결정한다. 현재 구체적인 기술이나 조건을 임의로 확정하지 않는다.

**실제 테스트 후 결정할 것**

- SSH 탐지의 인증 실패 횟수와 시간 범위
- 자동 차단 제외 IP의 구체적인 범위
- 자동 차단 지속 시간 또는 자동 해제 여부

→ 실제 피해 서버와 실습 환경의 테스트 결과를 바탕으로 설계에 반영하며, 최종 통합 검증 전에 확정한다.
