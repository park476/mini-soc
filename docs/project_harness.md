# 3. 프로젝트 한 줄 정의
======================================================================

Nginx 접속 로그와 Linux SSH 인증 로그를 수집하고,
서로 다른 형식의 로그를 공통 보안 이벤트로 정규화한 뒤,
설명 가능한 규칙 기반 탐지, 경보, 상관분석,
위험도 판단, 보안 사고 구분, 제한적인 자동 대응까지 연결하고,
그 근거와 실행 결과를 화면에서 확인할 수 있도록 하는
교육·발표용 소형 보안관제 시스템이다.

# 12. 피해 서버와 관제 서버 분리
======================================================================

피해 서버와 보안관제 서버는
논리적으로 서로 다른 시스템으로 취급한다.

피해 서버가 공격받는 것과
관제 서버가 함께 죽는 구조를 의도하지 않는다.

특히 DB를 하나의 공유 DB로 설계하지 않는다.

피해 서버 DB:

- 피해 웹 서비스에 DB가 필요할 경우 사용
- 테스트 계정
- 피해 웹 서비스 데이터

관제 DB:

- 보안 이벤트
- 필요 시 원본 로그
- 경보
- 상관분석 결과
- 위험도
- 보안 사고
- 대응 실행 결과
- 대응 검증 결과

교수가 피해 서버와 관제 서버가
DB 하나를 반드시 공유하라고 지시한 것이 아니다.

오히려 시스템이 과도하게 결합되는 문제를 질문한 것으로 이해한다.

단,
피해 서버와 관제 서버를
같은 물리 호스트의 Docker 환경에서 논리적으로만 분리한다면
물리적 완전 격리라고 주장하지 않는다.

강한 DoS나 호스트 전체 장애에는
동시에 영향을 받을 수 있다.

# 13. 로그 전달
======================================================================

피해 서버와 관제 서버가 분리되어 있으므로

"관제 서버가 피해 서버의 로컬 파일을 그냥 직접 읽는다"

는 구조를 기본 전제로 하지 않는다.

개념:

Nginx Log ─┐
           ├→ 로그 전달기 → 네트워크 → 관제 로그 수집기
SSH Log ───┘

"로그 전달기"는 역할 이름이다.

구현 기술은 현재 미정이다.

후보:

- rsyslog
- Filebeat
- 간단한 Python 전달기
- 기타 단순 전달 방식

과거 구조도에 Filebeat가 등장했다는 이유만으로
Filebeat를 확정하지 않는다.

선정은 STEP 1 / STEP 4 / STEP 5에서 한다.

선정 기준:

- 구현 난이도
- 안정성
- 학습 비용
- 로그 2종 지원
- Docker / Linux 환경 적합성
- 시연 안정성
- 시간

탐지 Rule에서도 중복 구현하지 않는다.

어떤 보안 이벤트를 보는가?

PATTERN

어떤 행동을 의심 행동으로 판단하는가?

GROUP

무엇을 기준으로 묶는가?

예:
- Source IP
- Username
- Path

WINDOW

시간 범위가 필요한가?

THRESHOLD

몇 회 이상인가?

OUTPUT

어떤 경보가 만들어지는가?

SEVERITY / 중요도

왜 그렇게 판단하는가?

EVIDENCE

실제 어떤 로그가 근거인가?

FALSE POSITIVE

어떤 정상 행동이 오탐될 수 있는가?

구현 전에 설명할 수 없는 Rule을 만들지 않는다.


======================================================================
# 16. SSH 대표 시연
======================================================================

대표 시연 시나리오:

SSH 무차별 대입 공격

통제된 공격 환경
→ 피해 Linux 서버 SSH 인증 실패 반복
→ 실제 SSH 인증 로그 생성
→ 로그 전달
→ 관제 서버
→ 정규화
→ SSH Brute Force 탐지
→ 경보
→ 자동 대응 조건 확인
→ 공격 Source IP 차단
→ 동일 환경에서 SSH 재시도
→ 실제 차단 확인

이 대표 시연은
자동 대응 End-to-End 검증용이다.

대표 SSH 시연 하나가
전체 프로젝트 검증을 모두 대신하지 않는다.

Correlation은 별도 시나리오로 검증할 수 있다.

# 17. 상관분석
======================================================================

최소:

1종

Correlation은 같은 Rule을 여러 번 세는 기능이 아니다.

목표:

종류가 다른 이벤트 / 경보 사이의 관계를 연결한다.

가능한 연결 기준:

- source_ip
- username
- destination
- timestamp
- event 순서
- 시간 Window

과거 논의 예:

동일 Source IP
→ 로그인 실패 반복
→ 로그인 성공
→ 필요 시 중요 자원 접근
→ 위험 상승
→ 보안 사고

이는 현재 유력 후보일 뿐
세부 조건이 확정되었다는 의미는 아니다.

특히:

"반복 실패 후 성공"

을 Detection Rule과 Correlation에 동시에 사용하여
같은 행동을 두 번 계산하지 않는다.

STEP 1 / STEP 4에서 역할을 결정한다.

둘을 같은 Entity로 취급하지 않는다.

예:

SSH Brute Force Detection
→ Alert

다른 관련 이벤트와 연결
→ Correlation

위험도 판단
→ Incident 생성 여부 판단

자동 대응은 반드시

경보 또는 필요한 탐지 결과
→ 자동 대응 조건

이라는 별도 흐름을 허용한다.

구체적인 자동 대응 Trigger는 아직 결정하지 않았다.
