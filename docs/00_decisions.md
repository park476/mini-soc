| 항목 | 확정 내용 |
|---|---|
| D1. 피해 서버 실행 위치 | 역할·배치 결정 확정: 교수님에게 빌릴 예정인 학교 Ubuntu 미니 PC 서버. 아직 대여되지 않았으며 장비 확보·환경 검증 전 |

## 2026-09-21 — STEP 1 DB 분리 및 격리 방향 추가 결정

근거: 사용자의 최신 명시적 결정. 아래 확정 내용은 문서상 결정이며 실제 구축·연결·동작 확인을 의미하지 않는다.

### 실행 환경 재확인

- 공격자: 학교 PC에서 실행하는 WSL Kali Linux.
- D1 피해 서버: 교수님에게 빌릴 예정인 학교 Ubuntu 미니 PC 서버로 역할·배치를 결정했다. 아직 사용자에게 대여되지 않았으며, 장비 확보·접속·네트워크 연결·로그 위치·동작 여부는 확인하지 않았다. 2026-09-22 교수님께 장비 대여를 요청할 예정이다. 구현 완료·구축 완료·동작 확인을 의미하지 않는다.
- D2 관제 서버: 사용자 개인 노트북의 WSL2 Ubuntu 환경.
- 공격은 졸업 프로젝트의 통제된 실습·시연 범위에서만 수행한다.

### DB 분리 — 확정

- 피해 서버와 관제 서버는 하나의 PostgreSQL DB를 공유하지 않는다.
- 관제 서버는 자체 PostgreSQL에 정규화된 보안 이벤트와 탐지·분석·대응 결과를 저장한다.
- 피해 웹서비스 DB는 필수로 확정하지 않는다. D21 피해 웹서비스 로그인/DB 필요 여부는 [결정 필요]로 유지한다.
- 피해 웹서비스 DB를 두더라도 관제 DB와 공유하지 않는다.

### D3 격리 방향 — 방향 확정, 세부 수준은 결정 필요

- 공격자·피해 서버·관제 서버를 서로 다른 실행 환경에 배치한다.
- 피해 시스템 데이터와 관제 데이터를 논리적으로 분리한다.
- 관제 서버가 피해 서버의 로컬 로그 파일이나 DB를 직접 공유·마운트해서 읽는 구조를 기본 전제로 하지 않는다.
- 로그는 피해 서버에서 관제 서버로 네트워크를 통해 전달한다.
- VLAN, 별도 서브넷 등 네트워크 수준의 세부 격리 방식은 아직 확정하지 않는다. 실제 학교 네트워크 연결 환경을 확인한 뒤 D3의 세부 격리 수준을 확정한다.

### 과거 구조도·구두 답변과의 관계

- 사용자 설명에 따르면 이전 교수님 제출용 구성도에는 피해 서버 DB와 관제 PostgreSQL이 별도로 표현되어 있었다. 이번 작업에서 과거 구성도 자체를 확인한 것은 아니다.
- 과거 대화에서 “같은 DB 공유”라고 답변한 적이 있더라도 현재 최신 결정은 DB 비공유 구조다.
- 최신 사용자 결정이 과거 구두 답변보다 우선한다. 과거 구성도에 피해 DB가 있다는 사실만으로 D21을 확정하지 않는다.

### 자동 대응 흐름 재확인

- 자동 대응은 상관분석이나 보안 사고 생성을 필수 선행 조건으로 하지 않는다.
- 경보 또는 필요한 탐지 결과가 자동 대응 조건을 만족하면 별도 흐름으로 실행할 수 있다.
- 구체적인 자동 대응 발동 조건과 IP 차단 구현 기술을 이번 결정으로 확정하지 않는다.

### 계속 미정인 항목

D3의 세부 네트워크 격리 수준, D4 로그 전달 기술, D14 IP 차단 구현 기술, D21 피해 웹서비스 로그인/DB 필요 여부 및 그 밖의 기존 미결정 사항은 이 기록 시점에는 유지했다. Filebeat, rsyslog, Python 전달기, UFW, iptables, nftables 중 어느 것도 당시 선택하지 않았다.

현재 단계는 STEP 1이며, STEP 2로 진행하지 않는다.

## 2026-09-21 — STEP 1 최소 구현안 사용자 결정

사용자가 제시한 최소 구현안을 최신 설계 결정으로 기록한다. 이전 기록의 해당 미정 상태를 대체한다. 기술 선택과 수치 지정은 실제 구축·테스트 완료를 의미하지 않는다. D1은 여전히 장비 대여·확보 전이며 D2와 공격자 배치는 유지한다.

PRD가 실제 테스트 후 결정하도록 남겼던 SSH 수치와 자동 해제 정책은 이번 사용자 결정으로 설계값을 지정했다. 실제 테스트 결과는 아직 없으며, 검증 후 변경이 필요하면 사용자에게 보고한다. PRD 자체는 수정하지 않는다.

### 남은 세부 결정과 실제 검증

- D4: 실제 로그 위치·형식, TCP 메시지 경계·전달 형식, 학교 LAN에서 노트북 WSL2 수집기까지의 연결 가능 여부는 확인 전이다.
- D5·D6: URI 구분·정규화 방식, 의심 경로 전체 목록과 일치 방식은 미정이다.
- D8~D10: 경보의 시간 기준, 점수 집계 대상·기간·반복 경보 중복 계산 방식, Low/Medium 경계는 미정이다. High는 70 이상으로 지정되었다.
- D14·D15: 원격 실행 권한·실제 SSH 포트·허용 목록의 구체적 IP는 확인·설계가 필요하다.
- D17: 재접속 실패 기록은 실제 차단 검증의 입력이다. 인증 실패나 서비스·네트워크 장애와 차단 효과를 구분하는 구체적 판정 근거는 후속 설계에서 정한다. 단순 접속 실패만으로 차단 성공을 단정하지 않는다.
- D18~D20: 저장 스키마, 무수신 시간 기준과 확인 단위는 미정이다. 무수신 상태만으로 전달 실패 원인을 확정하지 않는다.
- 기존 E1~E5의 데이터·API·화면·예외 정책 등 후속 설계와 실제 검증은 남아 있다.

## 2026-10-12 — 관리자 패널 SSH 차단 해제 MVP (사용자 최신 결정)

근거: 사용자의 최신 명시적 지시. 구현 단계(READY TO CODE 통과 후)의 결정이며 아래 기존 문서 내용보다 우선한다.

### 기존 문서와 달라지는 점

| 기존 내용 | 최신 결정 |
|---|---|
| D16: 자동 해제 없음, 관리자가 피해 서버에서 수동 해제 | 자동 해제 없음은 유지. 수동 해제 수단으로 Django 관리자 패널에서 superuser가 실행하는 원격 해제를 추가 |
| 02_flow_screens·03_wireframes·04_features_data_api: 웹 차단 해제 버튼·해제 API를 두지 않음 | React 관제 화면과 DRF API에는 여전히 해제 기능을 두지 않음. 해제는 Django Admin(세션 로그인·CSRF·POST)에서만 실행하고 React에는 Admin으로 가는 링크만 추가 |

위 문서 본문과 PRD는 수정하지 않았다. 이 기록이 해당 항목의 현재 상태다.

### 확정 내용

- 실행 권한: superuser만. 대상은 실행 성공(`succeeded`)한 `block_ssh` ResponseRecord만.
- IP·명령은 저장된 ResponseRecord.target_ip를 `ipaddress`로 검증해 고정 형식으로만 만든다. 요청 입력값은 사용하지 않는다.
- 순서: `sudo -n ufw status` 확인 → 해당 IP의 22/tcp DENY 규칙이 있을 때만 `sudo -n ufw delete deny proto tcp from <ip> to any port 22` → `sudo -n ufw status` 재확인. 규칙이 없으면 삭제 명령을 보내지 않는다.
- 별도 opt-in `RESPONSE_UNBLOCK_EXECUTE`(기본 False). `RESPONSE_EXECUTE`(자동 차단, 기본 False 유지)와 서로를 켜거나 요구하지 않는다.
- 감사 기록은 신규 `UnblockRecord`에 저장한다(요청 관리자, IP, 시각, 실행 결과, 해제 전·후 UFW 확인, 오류 종류: SSH 오류·sudo 거부·타임아웃 구분). 기존 ResponseRecord·ResponseVerification은 수정·삭제하지 않는다.
- 해제 명령 실행 성공과 Kali SSH 재접속 성공은 별개 항목이다. 재접속 결과는 실제 관찰 후 UnblockRecord에 따로 입력한다.
- 관리자 해제는 `run_analysis`·`run_responses`를 호출하지 않는다.
- 피해 서버 sudoers는 현재 허용된 192.168.1.4에 대한 삭제 명령 한 줄만 추가한다. 임의 IP로 확대하지 않으며 실제 장비에서 사용자가 직접 설정한다.
- 실제 미니 PC에 UFW 차단·해제 명령을 보내기 전에는 사용자 확인을 받는다. 테스트는 fake executor만 사용한다.
- 미니 PC의 Apache:80, Juice Shop:3000, Nginx:8080은 변경하지 않는다.

### 확인하지 못한 것

- 지시문의 `GPT 새 하네스.txt`, `졸업프로젝트용 GPT 하네스.txt`는 저장소에서 찾지 못했다. AGENTS.md, docs/PRD.md, docs/project_harness.md, 본 문서, docs/reference/handoff를 기준으로 했다.

근거: 사용자의 최신 명시적 지시. 같은 날 앞선 두 기록의 화면 구성과 "관리자 기능은 해제만"이라는 범위를 대체한다.

### 앞선 기록·기존 문서와 달라지는 점

| 기존 | 최신 결정 |
|---|---|
| 관리자 패널 메인이 ResponseRecord 카드 | 경보가 발생한 출발지 IP를 중복 없이 한 행씩 보여주는 관리 테이블. 검색·위험도 필터·정렬·새로고침 제공 |

### 확정 내용

- 현재 차단 상태는 피해 서버 `sudo -n ufw status`를 읽은 결과로만 판단한다. 과거 성공 기록은 이력으로만 표시한다. 상태를 읽지 못하면 변경 작업을 실행하지 않는다.
- 버튼: 미확인 → 상태 확인, 차단 중 → 차단 해제, 과거 차단 후 현재 해제됨 → SSH 재차단, 차단 이력 없는 승인 IP → SSH 차단. 모든 변경은 IP·포트·명령을 보여주는 확인 대화상자를 거친다.
- 수동 차단은 `ManualBlockRecord`에 관리자·IP·명령·실행 결과·UFW 전후 상태를 저장한다. 자동 대응 ResponseRecord(경보당 1건)는 다시 쓰지 않는다. 이미 차단 중이면 중복 규칙을 추가하지 않는다.

- 안전 스위치는 세 개이며 서로를 켜지 않는다: `RESPONSE_EXECUTE`(자동 대응, 기본 False 유지), `RESPONSE_UNBLOCK_EXECUTE`(해제), `RESPONSE_MANUAL_BLOCK_EXECUTE`(수동 차단, 신규, 기본 False).
- 피해 서버 sudoers는 넓히지 않는다. 첫 조치 대상은 192.168.1.4 하나다.
- 화면과 문구는 SSH(22/tcp) 차단으로만 표시하고 웹 접근 차단으로 표현하지 않는다.
- 이번 작업에서 미니 PC에 차단·해제·상태 조회 명령을 보내지 않았다. 테스트는 fake executor만 사용했다.

근거: 사용자의 최신 명시적 승인. 2026-10-12 "IP 중심 위협 관리와 수동 SSH 차단" 기록의 조치 가능 IP 조건(`RESPONSE_MANUAL_TARGETS` 정확한 IP)을 대체한다. 앞 기록은 이력으로 남긴다.

| 기존 | 최신 결정 |
|---|---|
| `RESPONSE_MANUAL_TARGETS`에 등록되고 Alert(종류 무관)가 있는 IP만 SSH 수동 차단 | `ssh_brute_force` Alert가 있는 IP를 superuser가 패널에서 선택. Nginx 경보만 있는 IP는 SSH 대상 아님. `RESPONSE_MANUAL_TARGETS`는 더 이상 사용하지 않음(변수는 호환을 위해 유지) |
| 패널이 `sudo -n ufw prepend/delete …`를 IP별 정확 sudoers 줄로 실행 | 패널은 root 소유 실행기 `/usr/local/sbin/mini-soc-sshblock block|unblock <ip>`만 호출. 실행기가 명령·IP 형식·주소 종류·보호 목록(필수)·실행 파일·경로·UFW 활성 여부를 자체 검증. sudoers에 ufw 와일드카드 권한 없음 |

확정 내용:
- 주소 규칙(웹 차단과 공통, `events/address_policy.py`): 공인 IP는 `ssh_brute_force` 경보 필수. 사설 IP는 `RESPONSE_SSH_PRIVATE_RANGES`와 미니 PC `/etc/mini-soc/ssh-private-allowed.txt`에 명시한 범위만(기본 비어 있음, 공격 장비 LAN IP 확인 후 /32). 웹 허용 범위와 별개.
- 차단 거부: 보호 목록(172.18.20.65, 172.18.20.161, 172.29.176.40, 119.194.231.131), 요청한 관리자의 접속 주소, 루프백·링크 로컬·예약·멀티캐스트·미지정·문서용 주소. 실행기는 호출 SSH 세션 출발지(`SSH_CLIENT`)도 거부하지만 조작 가능하므로 보조 방어선으로만 쓰고, root 소유 보호 목록 검사를 필수로 한다.
- 해제: 이 시스템이 만든 성공 차단 기록(자동 ResponseRecord 또는 ManualBlockRecord)이 있는 IP만. 사람이 만든 UFW 규칙은 패널에서 지우지 않는다. 주소 규칙이 바뀌어도 이 시스템이 만든 차단은 해제할 수 있다.
- 실행기는 `22/tcp DENY from <ip>` 한 형태만 추가·삭제한다. UFW enable/disable/reset/reload, 다른 포트·동작은 사용하지 않는다. UFW가 비활성이면 거부한다.
- 자동 대응(`response.py`, `RESPONSE_EXECUTE=false`)과 Django Admin 해제 경로는 기존 직접 UFW 명령과 정책을 유지한다. 웹 차단 기능·WebBlockRecord는 변경하지 않았다.
- 실제 효과 검증은 명령 결과와 분리: migration 0009(추가형, ManualBlockRecord 재접속 결과 3필드·UnblockRecord 확인 시각 1필드)와 `record_ssh_check`로 공격 장비의 새 SSH 접속 결과를 기록한다. 차단 검증 = UFW 규칙 있음 + 새 접속 실패, 해제 검증 = 규칙 없음 + 새 접속 성공.
- override 허용 키에 `RESPONSE_SSH_PRIVATE_RANGES`, `RESPONSE_MANUAL_BLOCK_EXECUTE` 추가(컨테이너 재생성 없이 SSH 차단을 끌 수 있게).
- 실증 네트워크: Kali 노트북은 현재 핫스팟 환경에서 미니 PC 22번에 직접 접근하지 못해 경로가 미확정이다. 공격 출발지는 관제 PC(172.18.20.65)와 달라야 하며 Cloudflare Tunnel을 거치지 않는 직접 TCP 22 경로가 필요하다.
- 첫 실차단은 15분 복구 타이머를 계획한다. 미니 PC sudoers·실행기 설치, UFW 변경, 실제 SSH 차단은 아직 수행하지 않았다.
