# STEP 2 — 사용자 흐름과 최소 화면 설계

작성 기준: 2026-09-21

## 1. 기준과 범위

기준 문서는 [AGENTS.md](../AGENTS.md), [PRD](PRD.md), [프로젝트 하네스](project_harness.md), [최신 사용자 결정](00_decisions.md), [STEP 1 요구사항](01_requirements.md)이다. 이전 문서의 미정·진행 대기 표현은 최신 사용자 결정과 이번 STEP 2 시작 지시에 따라 해석한다.

기본 사용자는 보안관제를 학습하고 시연하는 학생이다. 사용자 흐름 5개와 화면 4개로 정리한다. 목록과 상세는 같은 화면 안에서 항목을 선택해 확인하는 구조로 묶으며 별도 화면으로 늘리지 않는다. 아래 데이터는 화면에 필요한 의미를 나타내며 DB 필드나 API 명세를 확정한 것이 아니다.

- [설계 완료] 이 문서의 사용자 흐름과 화면 범위.
- [구현 예정] 모든 실제 데이터 연결과 화면 동작. 기존 Mock Data 기반 EventTable은 UI 초안이며 실제 데이터 UI 완료를 의미하지 않는다.
- [검증 예정] 피해 장비 대여·확보, 학교 LAN·WSL2 연결, 로그 위치·형식·IP·포트·권한 및 실제 동작. D1 피해 서버는 아직 확보 전이다.
- 이번에는 본 문서만 작성한다. STEP 3, 구현, 환경 구성은 수행하지 않는다.

복잡한 권한·계정 체계, 승인, 규칙 편집, Playbook, 공격 실행 UI를 추가하지 않는다. 공격 재현·UFW 규칙 확인·Kali 재접속·수동 차단 해제는 통제된 실습 환경의 작업이며 대시보드의 원격 조작 기능으로 만들지 않는다.

## 2. 시스템 처리와 화면의 관계

공통 처리: 피해 서버의 로그 발생 → rsyslog 전달 → TCP 5514 Python 수집기 → 파싱·정규화 → 관제 PostgreSQL 저장 → 탐지 → 경보.

분석 처리: 경보 → 관련 이벤트·경보 상관분석 → 위험도 판단 → 조건 충족 시 보안 사고.

자동 대응 처리: SSH brute force Alert → 허용 목록 확인 → 관제 서버에서 피해 서버로 SSH 원격 명령 → 피해 서버 UFW 차단 → 실행 결과 저장 → 실제 효과 검증 결과 기록.

조회: 관제 PostgreSQL의 기록 → Django/DRF API → React 화면. React는 PostgreSQL에 직접 접근하지 않는다. 화면 조회나 버튼 클릭이 자동 대응의 발동 조건이 되어서는 안 된다. 자동 대응은 상관분석·Incident 생성을 기다리지 않으며 대시보드가 꺼져 있어도 백엔드에서 동작할 수 있어야 한다.

화면 간 이동은 A에서 B·C·D로, C의 근거 경보에서 B의 관련 이벤트로, C와 D 사이의 연결된 경보·대응 기록으로 이어진다. 화면을 여는 순서는 시스템 처리의 실행 순서를 강제하지 않는다.

## 3. 사용자 흐름

### U1. 보안 이벤트 확인

**목표:** 실제 피해 서버 로그가 정규화·저장된 보안 이벤트와 연결되는지 확인한다.

**정상 흐름:**

1. 통제된 실습에서 피해 서버에 Nginx 접속 로그 또는 Linux SSH 인증 로그가 발생한다.
2. 피해 서버 rsyslog가 로그를 관제 서버로 전달한다. Nginx access.log는 imfile로 읽는다.
3. Python 수집기가 수신하고 파싱·정규화를 거쳐 SecurityEvent를 저장한다.
4. 학생이 A에서 수신 현황을 확인하고 B의 보안 이벤트 목록으로 이동한다.
5. 해당 이벤트를 선택해 로그 종류, 발생 시각, 출발지 IP, 행동·결과와 원본 로그 근거를 대조한다.

**실패·예외 흐름:**

- 초기 60초 무수신 또는 수신 오류는 A에서 전달 이상 정보로 확인한다. 이를 네트워크 장애 등 특정 원인의 확정으로 표시하지 않는다.
- 정규화 실패는 B 안의 실패 기록 영역에서 원본 로그와 실패 이유를 확인한다. 성공한 SecurityEvent와 구분한다.
- 저장 이벤트가 없을 때는 빈 목록을 표시하고, API 조회 실패는 별도의 조회 오류로 표시한다. 조회 실패를 로그가 없다는 뜻으로 처리하지 않는다.

**연결 완료 조건:** F1·F2·F6 — 두 종류의 실제 로그 수집·저장, 원본 대조, 실패 확인, 실제 API 조회.

### U2. 탐지 및 경보 확인

**목표:** 탐지 3종 각각의 적용 조건과 실제 근거를 설명한다.

**정상 흐름:**

1. 학생이 통제된 실습에서 규칙별 행동을 수행하고 U1의 수집·정규화 흐름으로 이벤트가 저장된다.
2. 백엔드가 아래 조건을 판단하고 해당하면 Alert를 생성한다.
3. 학생이 C의 경보 목록에서 해당 경보를 선택한다.
4. 규칙과 판단 근거를 확인하고 연결된 이벤트를 선택해 B에서 원본 로그를 대조한다.

| 규칙 | 화면에서 설명할 조건과 근거 |
|---|---|
| SSH brute force | 동일 IP에서 60초 안에 인증 실패 5회 이상. 관련 실패 기록·시각·횟수 |
| Nginx scan | 동일 IP가 60초 안에 404/403 응답을 발생시키며 서로 다른 URI를 10개 이상 요청. 응답 코드·URI·시각·서로 다른 URI 수 |
| Nginx suspicious path | query string 제외 URL path가 초기 목록의 경로와 정확히 일치하거나 그 하위 경로. 실제 path와 일치한 목록 항목 |

의심 경로 초기 목록: `/.env`, `/wp-admin`, `/wp-login.php`, `/admin`, `/phpmyadmin`, `/.git`, `/config`, `/backup`.

**실패·예외 흐름:** 조건을 충족하지 않는 정상 입력은 B에 이벤트가 있어도 해당 규칙 경보가 생기지 않을 수 있다. 경보가 없다는 사실을 수집 실패와 혼동하지 않는다. 근거를 조회하지 못하면 확인 불가 상태를 표시하며 근거를 만들어 채우지 않는다.

**연결 완료 조건:** F3·F6 — 탐지 3종의 실제 근거와 조건 대조, 정상 입력과 구분. SSH 대표 시연만으로 나머지 두 규칙 검증을 대체하지 않는다.

### U3. 상관분석·위험도·보안 사고 확인

**목표:** 경보 연결 이유와 점수·등급, Incident 생성 여부를 구분한다.

**정상 흐름:**

1. 동일 출발지 IP에서 SSH brute force 경보와 Nginx scan 또는 suspicious path 경보가 10분 이내 함께 발생한다.
2. 백엔드가 상관분석 결과와 연관 경보, 위험도 판단 근거를 기록한다.
3. 학생이 C에서 연결된 경보·시각·출발지 IP와 상관분석 성립 결과를 확인한다.
4. 탐지 종류별 기본 점수 1회와 지정 상관분석 +30, 최대 100의 점수 내역을 확인한다. 같은 종류의 반복 경보는 횟수만큼 가산하지 않는다.
5. Low 0~39, Medium 40~69, High 70~100의 등급을 확인한다. 상관분석 성립과 High 조건을 함께 충족하면 생성된 Incident를 확인한다.
6. 같은 C 화면에서 Incident에 연결된 원래 Alert를 확인하고 필요하면 B의 원본 근거로 이동한다.

점수 설명 예시: 판단 대상에 SSH와 스캔이 포함되고 지정 상관분석이 성립하면 40 + 30 + 30 = 100, High이다. SSH와 의심 경로라면 40 + 20 + 30 = 90, High이다. 이는 계산 예시이며 실제 실행 결과가 아니다. 판단 대상 기간·데이터 구조는 STEP 4에서 정의한다.

**실패·예외 흐름:** 출발지 IP가 다르거나 10분 조건을 충족하지 않으면 해당 상관분석은 성립하지 않는다. 단순 Alert를 Incident로 표시하지 않는다. 분석 결과가 아직 없는 상태와 조건 불충족 결과를 구분하며, 데이터 미조회 상태를 점수 0이나 분석 실패로 단정하지 않는다.

**연결 완료 조건:** F4·F6 — 상관분석 최소 1종, 연관 근거, 위험도 계산, Alert/Incident 구분. 대표 SSH 시연과 별도의 통제된 검증으로 확인할 수 있다.

### U4. 자동 대응 확인

**목표:** 차단 실행 결과와 실제 차단 효과 검증 결과를 각각 확인한다.

**정상 흐름:**

1. SSH brute force Alert 생성으로 자동 대응 조건이 충족된다.
2. 백엔드가 허용 목록을 확인한다. 관제 서버 IP와 관리 필수 주소는 제외하며 Kali 공격자 IP는 제외하지 않는다.
3. 백엔드가 피해 서버에 SSH 원격 명령을 보내고 UFW로 해당 IP의 SSH 접근을 차단한 실행 결과를 기록한다.
4. 학생은 C의 해당 경보에서 D의 대응 기록으로 이동하여 대상 IP·발동 근거·실행 결과를 확인한다.
5. 실습 환경에서 UFW에 대상 IP 차단 규칙이 실제 등록됐는지 확인하고 같은 Kali에서 피해 서버 SSH 재접속을 시도한다.
6. 규칙 존재와 해당 Kali의 접속 실패가 함께 확인된 검증 기록을 D에서 확인한다. 실행 결과와 검증 결과는 별도 정보로 표시한다.
7. 시연·테스트 종료 후 또는 오탐 시 관리자가 피해 서버에서 수동 해제한다. 자동 해제와 웹 차단 해제 버튼은 두지 않는다.

검증 근거를 저장하는 구체적 입력·수집 방식은 STEP 4/5에서 정한다. 여기서는 임의의 수동 성공 판정 버튼이나 자동 원격 검증 기능을 추가하지 않는다.

**실패·예외 흐름:**

- 허용 목록 대상은 차단하지 않는다. 대응이 없다면 실행 성공으로 표시하지 않으며 경보와 차단 제외 이유를 확인할 수 있게 한다.
- SSH 원격 명령 또는 UFW 실행 실패는 D에 실행 실패로 표시한다.
- 명령 성공 후 검증을 하지 않았거나 근거가 없으면 검증 미확인으로 표시한다.
- UFW 규칙 존재와 동일 Kali의 접속 실패 중 하나라도 확인되지 않으면 검증 성공으로 표시하지 않는다. 수행한 검증의 실패와 아직 검증하지 않은 상태를 구분한다.
- 대시보드 조회 장애가 있어도 백엔드 자동 대응 흐름은 화면에 의존하지 않는다. 조회 복구 후 저장 기록을 확인한다.

**연결 완료 조건:** F5·F6 — 자동 차단 발동·허용 목록 제외, 실행/효과 결과 구분, 검증 근거, 실패 확인, 화면·Incident에 의존하지 않는 대응. 실제 수동 해제 여부는 피해 서버에서 검증한다.

### U5. 대표 시연 흐름

**목표:** 통제된 대표 SSH 공격 1회 이상에서 실제 로그부터 차단 검증까지 연결해 설명한다.

**실습 준비:** 피해 장비 확보와 학교 LAN 연결, 실제 로그 및 관제 수집 경로, 허용 목록·차단 명령 권한을 먼저 검증한다. 이는 향후 시연 전제이며 지금 준비 완료로 간주하지 않는다.

**정상 흐름:**

1. 학교 PC의 WSL Kali에서 학교 Ubuntu 미니 PC 피해 서버로 SSH 인증 실패를 반복한다.
2. 피해 서버에 Linux SSH 인증 로그가 발생하고 rsyslog가 네트워크를 통해 전달한다.
3. 개인 노트북 WSL2 Ubuntu 관제 서버의 Python 수집기가 TCP 5514로 수신한다.
4. 로그를 파싱·정규화하고 관제 PostgreSQL에 저장한다.
5. 동일 IP·60초·실패 5회 이상 조건으로 SSH brute force Alert가 생성된다.
6. 허용 목록을 적용하고 자동 대응을 실행한다. 관제 서버 → 피해 서버 SSH 명령 → UFW 차단으로 이어진다. 상관분석·Incident를 기다리지 않는다.
7. UFW의 대상 IP 차단 규칙을 확인하고 동일 Kali에서 SSH 재접속을 시도한다. 두 검증 근거와 실행 결과를 구분해 기록한다.
8. 학생이 A → B → C → D 순서로 수신 현황, 원본 로그·이벤트, 탐지 근거·경보, 실행 결과·실제 차단 검증을 설명한다.
9. 관리자가 피해 서버에서 시연 차단을 수동 해제한다.

대표 SSH 시연에서 상관분석이나 Incident가 반드시 발생한다고 가정하지 않는다. 이 경우 C에서 실제 존재하는 경보·분석 기록만 설명한다. Nginx 두 규칙은 U2, 상관분석은 U3으로 별도 검증한다.

**실패·예외 흐름:** 수집·정규화·차단·효과 검증 중 확인되지 않은 단계는 성공으로 발표하지 않고 A~D의 해당 실패 기록으로 설명한다. 실제 통제 실습에서 확보한 예비 로그를 동일 파서·탐지 흐름으로 재처리할 수 있으나, 예비 로그 재생으로 실제 IP 차단 성공을 주장하지 않는다. 예비 로그 실행 도구나 별도 재생 화면은 추가하지 않는다.

**연결 완료 조건:** PRD §2 성공 기준 7과 F1~F3·F5·F6의 대표 시연 연결. 전체 프로젝트 완료에는 U2의 3종 탐지 및 U3의 상관분석 검증도 필요하다.

## 4. 최소 화면 설계

화면은 A~D 4개다. 정규화 실패는 B, 상관분석·위험도는 C, 실제 효과 검증은 D에 포함하므로 추가 화면이 필요하지 않다. 정보 배치·와이어프레임은 STEP 3에서 설계한다.

### A. 관제 대시보드

- **목적:** 현재 수집 상태와 저장된 주요 결과를 간단히 확인하고 근거 화면으로 이동한다.
- **확인 정보:** 마지막 로그 수신 시각, 수신 오류, 초기 60초 무수신에 따른 전달 이상 표시. 최근 보안 이벤트·경보·보안 사고·대응 결과의 요약과 상세 연결. 실행 성공과 효과 검증 성공은 요약에서도 구분한다.
- **주요 행동:** B·C·D의 관련 목록 또는 기록 열기. 조회를 다시 수행해 최신 저장 기록 확인.
- **데이터 연결:** F1 수신 상태, F2 이벤트·실패 정보, F3 경보, F4 보안 사고·위험도, F5 대응 결과를 DRF API로 조회한다. 새로운 통계·분석 기능이나 장식용 차트를 추가하지 않는다.
- **검증할 완료 조건:** F1의 전달 이상 확인, F6의 실제 데이터 조회와 상세 근거 연결. 요약만으로 탐지·차단 성공을 검증 완료로 판정하지 않는다.

### B. 보안 이벤트 목록/상세

- **목적:** 정규화된 이벤트와 원본 로그를 대조한다.
- **확인 정보:** 로그 종류(Nginx/SSH), 발생 시각, 출발지 IP, 행동·결과, 원본 근거. 선택한 이벤트에 실제 존재하고 규칙 설명에 필요한 SSH 인증 결과 또는 Nginx URI·응답 코드 등을 표시한다. 같은 화면의 정규화 실패 영역에서 실패 원본과 이유를 확인한다.
- **주요 행동:** 목록 항목 선택, 상세·원본 근거 확인, C에서 연결한 근거 이벤트 확인 후 해당 경보로 돌아가기. 성공 이벤트와 실패 기록을 구분해 조회한다.
- **데이터 연결:** SecurityEvent, 원본 로그 또는 원본 참조, 정규화 실패 기록. 데이터 필드·저장 구조는 STEP 4에서 정의한다.
- **검증할 완료 조건:** F2의 두 로그 정규화·저장·원본 대조·실패 보존, F3의 탐지 근거 추적, F6의 실제 API 데이터 표시.

### C. 경보·보안 사고 목록/상세

- **목적:** 무엇 때문에 경보가 발생했고 어떤 경보가 하나의 보안 사고로 연결됐는지 설명한다.
- **확인 정보:** Alert와 Incident를 명확히 구분한 목록, 규칙 이름·조건, 출발지 IP·발생 시각, 관련 이벤트, 상관분석 결과·연결된 경보와 10분 조건의 근거, 위험도 점수·등급·점수 내역, Incident 생성 근거, 연결된 대응 기록.
- **주요 행동:** Alert 또는 Incident 선택, 같은 화면에서 연관 경보와 분석 내역 확인, B의 근거 이벤트 또는 D의 대응 기록 열기.
- **데이터 연결:** Alert, 탐지 조건과 근거 이벤트 연결, 상관분석 결과, 위험도 판단 결과, Incident, 관련 대응 참조. 실제 관계와 API 명세는 STEP 4에서 설계한다.
- **검증할 완료 조건:** F3의 탐지 3종과 로그 근거, F4의 상관분석·점수·등급·Incident 기준, F6의 연결 조회. 같은 종류의 반복 경보 수와 위험도 점수를 혼동하지 않는다.

### D. 자동 대응 결과/검증 화면

- **목적:** 어떤 경보로 차단이 실행됐고 실제 차단 검증이 완료됐는지 구분한다.
- **확인 정보:** 대상 IP·피해 서버, 발동 Alert, 허용 목록 제외 여부와 이유, 대응 시각과 실행 성공·실패, 검증 결과, UFW 대상 규칙 존재 확인 근거, 동일 Kali의 SSH 재접속 결과. 검증 미확인·실패·성공은 명령 실행 상태와 별도로 표현한다.
- **주요 행동:** 대응 기록 선택, 실행 결과와 검증 근거 대조, C의 발동 경보 및 B의 로그 근거로 이동. 이 화면은 결과 조회용이며 차단 승인·실행·해제·성공 강제 지정 버튼을 추가하지 않는다.
- **데이터 연결:** 자동 대응 조건 확인 결과, 실행 결과, 효과 검증 결과 및 두 검증 근거, 발동 Alert 참조. 제외·미실행 상태를 포함한 기록 구조와 근거 수집 경로는 STEP 4/5에서 정한다.
- **검증할 완료 조건:** F5의 실행/검증 결과 분리, 허용 목록 제외, 실행 실패·검증 실패 표시, UFW 규칙과 동일 Kali 접속 실패의 동시 확인, F6의 실제 대응 기록 조회.

## 6. 공통 표시 원칙과 후속 설계

- 모든 화면은 실제 API 기록을 기준으로 한다. Mock UI, 계산 예시, 예비 로그 재생 결과를 실제 통합 동작 증거로 바꾸어 표현하지 않는다.
- 비어 있는 목록, 조회 중, 조회 오류, 결과 미확인은 성공·정상 결과와 구분한다. API 조회 실패를 시스템 분석·대응 자체의 실패로 단정하지 않는다.
- 수신 시각·이벤트 시각·경보 시각·대응 시각은 역할을 구분해서 설명한다. 구체적인 시간 필드·표시 방식·판단 시간 기준은 STEP 4에서 정한다.
- 실제 기록에 없는 값은 만들어 표시하지 않는다. 화면에 필요한 정보와 저장 데이터·API의 연결은 STEP 4에서 검토한다.
- 대시보드 종료 상태에서도 백엔드가 자동 대응하고 결과를 저장할 수 있어야 한다. 향후 검증은 화면을 다시 열어 실제 저장 결과를 대조한다.
- STEP 3: 네 화면의 정보 우선순위와 목록·상세 배치. STEP 4: 데이터 스키마·API·위험도 판단 대상 기간·검증 근거 저장 및 조회. STEP 5: 전달·권한·환경·검증 세부. 이러한 후속 설계는 이번 STEP 2의 신규 사용자 결정 요청이 아니다.

## 7. STEP 2 완료 판정

요청한 5개 사용자 흐름의 정상·실패 경로와 4개 화면의 목적·정보·행동·데이터 연결·검증 조건, 흐름-화면 연결표를 정리했다. PRD와 STEP 1의 기능 범위 내에서 구성했으며 신규 사용자 결정이 필요한 항목은 없다.

STEP 2 문서 설계는 완료했다. 실제 구현·검증은 예정 상태다. STEP 3은 진행 가능한 상태이나 이번 작업에서는 시작하지 않는다.
